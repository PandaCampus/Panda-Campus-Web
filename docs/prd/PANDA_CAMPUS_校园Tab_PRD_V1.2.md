## 01｜定位、用户与阶段边界

### 1.1 产品目标

- 解决校园**本地数据碎片化、熟人/组织关系弱连接、信息难以形成现实行动**的问题；不以无限信息消费和停留时长为增长目标。
- 用户在低阅读成本下完成：**发现信息 → 核对可信状态 → 找到对应负责人/组织/地点 → 执行下一步行动**。
- 对开发而言，验证一条稳定链路：**运营录入 → 审核发布 → 数据库查询 → 统一卡片渲染 → 二级微应用/真实功能跳转**。

### 1.2 主要用户

- **学生**：查询岗位、附近商家、社团名片与活动；可进入真实主体主页。
- **信息责任方**：学校组织、社团负责人、合作企业/商家；V0 通过 SFOS 代理录入，后续可授权自行维护。
- **SFOS 运营**：在独立后台录入、核验、更新数据；后台**不在本篇校园前端 PRD 的界面范围内**，仅定义接口依赖。

### 1.3 两阶段路线：第一阶段先发现，第二阶段再生产与合作

**第一阶段（本 PRD 当前实施范围；由 SFOS 代理运营）**

- **P0 必做**：SFOS 录入与审核四类真实校园信息；数据库支持查询、编辑、下架、过期与主体归属；校园信息流从数据库读取、默认大图卡、双列橱窗/列表语义缩放、基础搜索与筛选、信息卡只读二级页；**胖达使用同一数据库进行百科式问答、事实检索及相关信息推荐，返回真实 Card ID**；空结果、权限和失效信息处理。
- **P1 数据条件具备时做**：真实坐标驱动的地点地图同框视图、地点卡片集合、主体主页基础版；如果地图数据暂缺，不应阻塞 P0 核心闭环。
- **第一阶段可用动作**：仅「查看」「联系」「查看官方报名/申请方式」等已存在的真实通道；不伪造用户已经报名、预约、申请或付款的结果。
- **第一阶段验收链路**：SFOS 代理上传真实数据 → 审核并进入数据库 → 学生搜索/浏览可找到 → 胖达依据数据库返回同一个 `card_id` 与可核验信息 → 点击卡片进入只读 Mini-App/官方联系入口。

**第二阶段（规划，不作为第一阶段开发完成的前置条件）**

- **主体自主发布**：人、组织、商家获得核验及管理权限，通过胖达表达发布意图；Agent 从文字/图片/文件抽取主体与内容属性，生成结构化草稿；发布主体人工确认，再经过适用的校方/平台审核，写入本体活动账本并正式发布。
- **主体维护与合作**：真实主体可管理自己发布的卡片、版本、地点与关系；支持发起招募、报名、合作意向或其他**真实启用的 Mini-Contract**，并记录同意、执行、反馈和结果。
- **权限底线**：Agent 不擅自公开发布、不冒用经营者或负责人；活动合约不是点击按钮就自动形成的法律合同。

**不是当前试点目标**：独立短视频社区、仿 Instagram 创作流、自研支付托管、未接入的图书馆座位预约、室内 3D 数字孪生、无来源的实时客流或评分。阶段任务、依赖与人工进度填写详见单独的《开发路线与进度 V1.1》。

### 2.2 页面跳转树

```text
校园 Tab（C-01 / C-02 / C-03）
├─ 搜索 C-04 ──> 搜索结果（沿用当前卡片密度）
├─ 筛选 C-05 ──> 过滤后的信息流 / 地点结果
├─ 地点 C-06（同层替换中间内容）──> 地标 C-07（地图内抽屉）──> 关联卡片 ──> Mini-App
├─ 图片 / 视频 ──> 媒体预览 C-14
├─ 卡片正文 ──> Card-to-Mini-App（C-08/09/10/11）
│   ├─ 责任主体 / 主办方 / 经营者 ──> 主体主页 C-12 / C-10 / C-09
│   └─ 相关地点 ──> C-06（定位并选中地点）
└─ 卡片关键 CTA ──> Button-to-Mini-Contract C-13
    └─ 真实操作结果/原服务状态回流原卡片
```

**返回规则**：`feedDensity` 与 `viewMode` 分离；从信息流点「地点」保存当前密度与滚动锚点，切入地图只更新中间视口；再次点「地点」回原信息密度。二级页返回来源视图，保留筛选/分类/地图中心/选中地点；不因二级访问创建重复信息卡。

## 03｜全局 UI 框架：只定义校园 Tab

### 3.1 顶部第 1 层：品牌与系统控制

- 左：**PANDA CAMPUS** 纯文字品牌。`PANDA` 黑色，`CAMPUS` 品牌黄色；**不加熊猫 Logo、头像或学校名称替代**。
- 右：微信小程序**系统胶囊**，位置由真实运行环境决定；禁止自画重叠的伪胶囊。
- **V1.2 默认背景**：页面顶部以**不透明白色 `#FFFFFF`** 为基底。若保留旧版极淡校园照片，只允许在品牌层作为非强制装饰并加足够白色蒙版；地图态顶部切换渐变磨玻璃，不能因底图而移动品牌或系统胶囊。
- 第 1 层固定；依实际状态栏、安全区和胶囊位置计算左侧可用宽度，不以设计稿中的固定绝对坐标写死。

### 3.2 顶部第 2 层：主体与沟通

- 左侧：圆形头像 + 账户显示名（单行溢出省略）；点击头像进入**当前用户自己的公开主体主页**，不是「我」工作台的替代品。
- 右侧：**触达**（NFC/二维码等触达能力）与**消息**（站内沟通），仅两个独立**横向长方形图文按钮**；按钮内部必须**图标在左、文字在右**，不能只显示图标；独立点击热区至少 44×44 CSS px。
- 不把触达/消息与下方的筛选/地点合并成一组，也不增加顶部社交账号第三按钮。

### 3.3 顶部第 3 层：信息检索

- 左：搜索框。提示语建议「搜索就业、商家、社团、活动…」，不必罗列所有业务细分。
- 右：**筛选**与**地点**是两个尺寸一致的**近正方形按钮**，内部**图标在上、文字在下**，内容居中，区别于上一层的横向长方形按钮。
- 下：分类横排 **全部｜就业｜商家｜社团｜活动**；选中项用短黄下划线（不是满屏彩色 Tab）。分类可横向滚动，但 V0 五项优先单行可见。

### 3.4 四个按钮的明确视觉规范（开发必须遵循）

- **触达（第 2 层）**：轮廓为横向圆角长方形，建议视觉宽 **70–78 px**、高 **40–44 px**、圆角 **10–12 px**；左侧是**四角开口的 NFC 扫描框线性图标**（框内标示 `NFC`，跟随实际触达能力），右侧明确标注**「触达」**。图标约 16–18 px，字约 12–13 px，图文间距 5–6 px；内部横排、垂直居中。
- **消息（第 2 层）**：与触达相同的横向圆角长方形尺寸和对齐方式；左侧是**线框信封图标**，右侧明确标注**「消息」**。有未读消息时，信封图标的右上角叠加**小黄色圆点**（建议 5–6 px），无未读时隐藏；**不以铃铛或聊天气泡代替信封**。两个按钮并列，按钮间距建议 8 px。
- **筛选（第 3 层）**：独立、近正方形的圆角按钮，建议视觉宽高 **50–54 px**、圆角 **10–12 px**；**上方漏斗线框图标（约 17–19 px）＋下方「筛选」文字（约 10–11 px）**，垂直排列、水平居中，图文间距 2–4 px。点击进入 C-05 筛选面板。
- **地点（第 3 层）**：与筛选完全一致的近正方形外框、尺寸和排版；**上方地图定位图钉线框图标＋下方「地点」文字**，垂直排列、水平居中。点击进入 C-06 地点地图；**不得替换成「视图」或四格布局图标**。
- **分层与自适应**：第 2 层的「触达／消息」在头像与名称的**右侧独立横排**；第 3 层的搜索框在左侧弹性伸缩，「筛选／地点」在右侧并排，间距建议 8 px；**第 2 层长方形横向图文，第 3 层近方形纵向图文，二者不可混用**。在 375/390/430 CSS px 和微信真机安全区下均不得重叠、挤压或换成只显示图标；如宽度不足，应优先让搜索框收缩，实际触控热区均不少于 44×44 px。
- **基础视觉状态**：默认白底或高透白底、1 px 中性浅灰描边、线性深色图标和文字；按下态为轻灰底，禁用态降低对比并解释原因。未读状态仅由消息小黄点表达，**不使用额外独立消息按钮**。

### 3.5 顶部背景状态（V1.2 增补，不改按钮几何）

- **Feed / 搜索默认**：品牌、主体、搜索、分类四层都以白色基底呈现。
- **Map 地点浏览**：这四层仅背景切换至纵向白色渐变磨玻璃（建议 `rgba(255,255,255,.92 → .66)` + `blur(14px)`），图标与文字、按钮排布、分类标签和点击热区原位不变。地图可视觉上延伸到玻璃层后方作为非交互衬底，但手势命中只能在分类下方内容视口。
- **Bottom Tab**：仍为 `#FFFFFF` 不透明白色，绝不应用 blur 或随地图背景透明；包括安全区保持原高度。
- 真实图像和地图底色复杂时增加白色遮罩；设备不支持模糊时回退纯白/高遮罩。详见《地点地图 UI 与交互规范 V1.2》。

### 3.6 底部全局导航

- 三个固定、均分的**纯文字** Tab：**校园｜胖达｜我**；不允许在此加入任何图标、独立消息 Tab 或额外入口。
- 当前页用文字加粗和一条短细黄色下划线表示。
- 本 PRD 只规定本页点击另两个 Tab 的全局导航行为，不涉及其内部布局。

## 04｜分类体系、命名与配色

### 4.1 首批四类业务

| 内部类别 | 前台入口 | 大标签（≤2 字） | 颜色 | 含义 | 主体归属 |
|---|---|---|---|---|---|
| `opportunity` | 就业 | **就业** / **创业** | 蓝色 | 招聘、实习、兼职、创业机会与就业信息 | 企业/组织/发布责任人 |
| `merchant` | 商家 | **商家** | 黄色 | 校园周边商家、商品/服务和经营信息 | 商家主体 → 经营者/组织 |
| `identity` | 社团 | **社团** / **组织** / **个人** | 紫色 | 社团及个人名片、组织介绍、负责人联系 | 人/组织主体 |
| `event` | 活动 | **活动** | 绿色 | 讲座、赛事、交流、招新活动等具体事件 | 主办组织/负责人 |

**名称原则**：一级分类是学生可懂的业务入口；内部实体类型、内容属性、功能能力彼此分离。首页「社团」是一项易懂的快捷入口，**紫色体系不仅限于社团**，个人名片通过搜索与关联主体进入，不增加首页第五业务分类。未来新增类别需有明确的持续数据供给和不同用户任务，不因数据库新增类型自动增加首页 Tab。

### 4.2 标签、关键属性和功能不要混用

- **大标签**：内容类别，用色唯一，最多 **2 个汉字**，且**必须与标题处于同一行，紧贴标题左侧**。
- **小标签**：1–3 个有助于决策的客观属性，例如「线下」「免费」「招新中」「可咨询」；避免堆砌「校园」「好看」一类模糊标签；如为业务状态，应由真实数据驱动。
- **关键数据**：根据内容类型优先展示剩余名额、申请截止、公开真实评分等；**真实浏览量严格大于 1,000 才展示**，等于 1,000 不展示。后台可存真实计数，不因前台隐藏而修改原值。
- **功能能力**：报名、咨询、申请、加入、查询、展示等是可执行能力，不是装饰标签。没有真实接口、责任人或可行的人工处理渠道，就不允许伪装成已实现操作。
- **CTA**：按操作选择动词，如「查看」「申请」「咨询」「加入」「报名」「领券」；默认品牌黄色，不跟随业务类别改变按钮颜色。


### 4.3 第一阶段四类信息：采集字段与入口能力（交付开发的数据标准）

**固定首页分类**：`全部｜就业｜商家｜社团｜活动`。`全部` 只是聚合视图，不是第五个内容类别。内部四类 `opportunity / merchant / identity / event` 保持稳定；四类卡可以互相关联，但不因某个内容同时具备多种属性而建立重复主记录。

| 类别与颜色 | 内容细分（作为内部属性，非首页新 Tab） | 第一阶段代理采集的最小字段 | V0 卡片 CTA 与二级页 | 第二阶段才逐步开放的能力 |
|---|---|---|---|---|
| **就业/创业 · 蓝** `#3478F6` | 实习、兼职、校招、招聘、创业招募/合作 | 岗位/机会名称、发布企业/组织及负责人关系、岗位类型、申请期限（如有）、地点或工作方式、要求与联系/官方申请入口、核验日期 | **查看岗位 / 查看申请方式 / 联系**；岗位信息 Mini-App | 主体自行发岗、在线投递、申请确认、合作意向合约 |
| **商家 · 黄** `#F7BE22` | 餐饮、美妆、生活服务、校园优惠等 | 商家名、经营主体及经营者关系、服务/商品、营业或服务时间、服务范围/地点、价格（若确认）、真实咨询方式、更新日期 | **查看服务 / 联系商家**；商家主体主页与服务集合 | 商家自行上新/报价、预约、交易与履约评价（按实际接入） |
| **社团／主体名片 · 紫** `#9258D8` | 社团、校园组织、个人/团队公开名片 | 主体名称与类型、简介、负责人（经授权）、公开联系渠道、组织活动、所在地、招新/合作状态（如有） | **查看名片 / 联系负责人**；主体主页及关联活动 | 自主维护主页、加入申请、成员关系确认与项目协作 |
| **活动 · 绿** `#25A96B` | 讲座、比赛、交流、招新活动、校园活动 | 活动名称、主办方及责任人、开始/结束时间、地点、参与条件、名额/费用（若真实）、报名方式、有效状态 | **查看活动 / 查看报名方式**；活动 Mini-App | 自主发布活动、报名/签到、活动履约与反馈 |

**数据代理录入规则（第一阶段）**：上传人 `created_by` 必须记录为实际 SFOS 操作者；信息原归属主体 `publisher_entity_id`、责任主体 `responsible_entity_ids` 和代理关系 `on_behalf_of` 分别记录，不能将代理录入误写为校方或商家的授权自发布。缺少可靠来源或联系权限的记录保持草稿，不直接对外显示。

**信息小标签与功能能力必须分离**：`在线 / 免费 / 截止日 / 招新中 / 学生优惠` 等是有数据依据的内容属性或状态；`咨询 / 申请 / 加入 / 报名 / 预约` 必须对应 `capability_id`、执行者、前置条件和真实可用的处理方式。前台仅展示已启用的功能，不为了四类模板外观一致而伪造按钮。

### 4.4 分类检索与首页展示的边界

- **基础分类**只收敛四类：首页显示 `全部｜就业｜商家｜社团｜活动`，大标签最多两字、紧贴标题左侧；就业类别中的「创业」是细分标签，组织/个人名片采用紫色体系但不挤占新首页分类。
- **原始资料与已发布卡片分开**：原始文件、海报、图片先作为档案资产保存；审核提炼后的 Information Card 才进入对外搜索/浏览及胖达检索。
- **筛选维度来自字段**：就业按工作形式/截止时间筛；商家按类型/价格（仅有报价时）筛；社团按方向/招新状态筛；活动按时间/报名状态筛。不能将「就业、免费、周末、可申请」做成互不区分的扁平标签墙。
- **统一查询过滤**：默认仅检索审核通过、未失效且用户具有访问权限的卡片。地图只显示有真实坐标与明确空间关系的记录。

## 05｜Information Card 标准与三级语义缩放

### 5.1 统一字段顺序

**媒体 → 大标签＋标题 → 时间 → 地点 → 关键小标签 → 关键数据 → 关键 CTA。**

- 媒体可为图片、视频封面或默认中性色占位。媒体区域点击打开媒体/详情，**不自动点赞或收藏**。
- 大标签和标题是一个阅读单元；标题本身可折行，标签仍紧贴第一行标题左侧。标签最多两汉字。
- 时间指发生/营业/报名截止/信息有效时间，应标明类型；没有时间信息不应补造。
- 地点可点击，打开对应地点主体的地图位置/地点集合；线上信息注明「线上」，无坐标不强制上图。
- 关键小标签依场景优先 1–3 个；关键数据来自真实账本或业务数据。
- CTA 始终在信息区右下角；未开放真正可执行能力时显示「查看」「联系」等诚实替代方式，或禁用并解释原因。

### 5.2 三档视觉密度

| 规则 | 大图卡片（默认） | 双列橱窗 | 紧凑列表 |
|---|---|---|---|
| 结构 | **1 列，媒体在上** | **2 列，媒体在上** | **1 行一条，缩略图在左** |
| 媒体 | 建议 16:9、可轮播 | 建议 4:3 | 建议 68×68 px 左侧方图 |
| 标题 | 1–2 行 | 1–2 行、优先一行 | 1 行优先，超长省略 |
| 时间 / 地点 | 两独立行 | 两短行 | 短行或适度合并但语义不丢失 |
| 小标签 / 数据 | 1–3 小标签 + 关键数据 | 最重要 1–2 项 + 可用关键数据 | 最重要 1 项，尽量不换行 |
| CTA | 右下独立醒目按钮 | 右下小按钮 | 右端紧凑按钮；纯「>」只表示进入详情 |
| 社交动作 | 按卡片能力启用 | 仅在适用且有空间时显示 | 默认不常驻，详情可用 |

**缩放手势**：在信息流区域双指捏合缩小为「大卡 → 橱窗 → 列表」，反向张开放大；触发有短暂、克制的状态提示，动画约 180–240 ms（建议值）。切换不修改筛选条件、排序、Card ID、点赞/行动状态或位置锚点。

**无障碍入口**：由于双指手势不可被所有用户发现，筛选面板底部可提供「浏览密度：卡片｜橱窗｜列表」文字切换选项，**不在顶部搜索栏增加第四个视图按钮**。

### 5.3 卡片互动机制

- 普通业务卡**不强制**显示点赞、夸夸、转发完整三按钮；支持社交表达的内容按 `social_capabilities` 决定是否展示，避免 V0 信息流拥挤。
- 若启用「点赞」，则**点赞＝喜欢并可找回**，不再有图片右上角收藏图标或独立收藏按钮；点赞/取消反映同一条关系状态。
- 夸夸用于正向表达；信息纠错、商家投诉和履约问题走独立反馈能力，不能被夸夸替代。
- 转发分享**同一个 Card ID** 的引用与受权限控制的展示，不复制新的权威信息源。

## 06｜搜索：快速检索，不代替胖达复杂判断

1. 点击搜索框进入 C-04，自动聚焦键盘；可以输入岗位、机构、活动、商家及人名。
2. 支持关键词包含与基础同义词匹配（如「实习」「兼职」），返回统一信息卡结果；按审核状态、有效期和可见范围过滤后再返回。
3. 默认搜索结果沿用用户当前密度状态；搜索结果支持继续筛选并在信息流 / 地图之间切换。
4. 搜索建议仅来自数据库真实名称和可公开的热门关键词；不以模型幻觉补全不存在的内容。
5. 空结果：显示「没有找到符合条件的信息」，提供「清除筛选」「换个关键词」；网络失败有「重试」，无权限信息不可出现在结果里。

> **V0 边界**：关键词 + 基础多字段检索即可；复杂个性化意图理解属于「胖达」工作台，不在校园首页搜索中另造 Agent 对话。


### 6.1 与胖达 Agent 的检索与百科式推荐联动（第一阶段必做）

**这里定义校园数据服务接口，不设计「胖达」Tab 的聊天页面。** 学生可在胖达输入「图书馆附近有哪些招人兼职」「有什么适合设计方向的活动」等问题；Agent 解析意图后调用数据库查询工具，结果应来自本期四类已核验的校园卡片。

1. **意图抽取**：关键词、类别、有效时间、地点、公开属性；缺少关键信息时可以追问，但不要求用户填写复杂筛选表。
2. **数据检索**：调用权限过滤后的 `listCards / getCard / getEntity`（或等价只读工具），由数据库返回真实字段、`card_id`、`updated_at` 和关联主体；不让语言模型直接写入数据表或编造结果。
3. **百科式问答**：将检索到的本地档案整理为简短事实说明，例如招募要求、组织介绍、活动安排；有明确失效/不确定状态时如实提示。回答与推荐卡片可打开原卡及责任主体。
4. **相关性推荐**：第一阶段只需可解释的关键词/类别/时间/地点/有效性排序；个性化心智模型并非 P0 必须完成。推荐应能说明依据，不能用凭空生成的评分、名额和热度制造说服力。
5. **异常与回写**：无匹配时明确说「数据库暂无相关信息」，网络异常可重试；被下架或过期的卡片不能继续作为有效推荐结果。浏览、搜索日志与反馈在取得适当权限后记录，用户私密对话不自动进入公开账本。

**验收重点**：新增一条经审核的真实信息后，校园搜索与胖达问答应能返回同一 `card_id`；修改与下架会在两处同步；没有证据的事实不得由 Agent 补全。

## 07｜筛选：维度 → 筛选项 → 组合结果

### 7.1 V0 筛选面板

- 入口：点击「筛选」，右侧或底部弹出抽屉；显示「筛选」标题、**重置**、各维度和**应用筛选**。
- 通用维度按顺序：**类别｜时间｜地点｜关键属性｜排序**。费用、评价仅在真实数据覆盖对应业务时出现，不为所有卡强加空维度。
- **类别**：全部/就业/商家/社团/活动，与首页快捷分类双向同步。
- **时间**：不限/今天/明天/本周/本周末/自定义。不同内容的时间类型按类别确定，如活动开始时间、岗位截止时间、商家营业时间。
- **地点**：校内/指定地点/附近/线上；没有定位授权允许手动选择校区或地点。
- **关键属性**：按所选类别动态生成，不能把所有词混成一堵标签墙。
- **排序**：推荐（有规则时）/最新发布/即将开始/距离最近（有坐标才可用）。

### 7.2 类别专属属性

| 类别 | 仅在适用时展示的筛选维度 |
|---|---|
| 就业 | 实习/兼职/全职/创业；线上/线下；有无经验要求；薪酬有无公开；截止日期 |
| 商家 | 服务种类；价格带（有报价时）；营业状态（已核验时）；是否可咨询/预约 |
| 社团 | 组织方向；招新状态；活动频次；是否开放联系 |
| 活动 | 报名中/已结束；费用；线上/线下；参加资格；剩余名额（有真实数据时） |

**布尔逻辑**：跨维度默认 AND；同一维度多选默认 OR。筛选变化可以预览结果数量，但必须以查询后实际返回的记录计数为准，不展示演示计数。点击应用后关闭面板，保留当前密度与滚动策略（必要时回到结果顶部）。点击重置清空所有条件、恢复首页分类选择状态。

## 08｜地点地图：同一校园页的空间视图（V1.2 核心修订）

### 8.1 从二级地图改为同框视图

地图通过第 3 层「地点」按钮进入，是 `viewMode = map`，**不新开一套独立顶部/底部页面**。`viewMode`（信息流/地图）与 `feedDensity`（大卡/双列/列表）独立保存；地图只占第 4 层分类栏下缘到全局底部栏上缘的**中间内容视口**。再次点「地点」返回原来的卡片密度和滚动位置。

**强制不变**：首层 PANDA/CAMPUS 字标与微信原生胶囊；第二层头像、横向长方形触达与消息；第三层搜索、近方形纵排筛选与地点；第四层 `全部｜就业｜商家｜社团｜活动` 原顺序原位置；底部白底纯文字「校园｜胖达｜我」。筛选、类别和搜索由信息流/地图共用。

### 8.2 视觉状态：默认白底，地图态顶部玻璃，底部不玻璃

| 固定区域 | 信息流默认 | 地图状态 |
|---|---|---|
| 第 1–4 层顶部 | 不透明白底；保持所有控件形状和位置 | 白色纵向渐变磨玻璃，建议顶部 `rgba(255,255,255,.92)` 到分类下缘 `rgba(255,255,255,.66)`，`blur(14px)`；**布局不变** |
| 分类栏下方中间区域 | 大图卡片 / 双列橱窗 / 列表 | 授权真实底图、地标、地点卡片抽屉 |
| 底部栏（含安全区） | 不透明 `#FFFFFF`，纯文字 3 Tab | **仍然不透明 `#FFFFFF`，不加 blur、图标或额外导航** |

玻璃视觉可利用地图背后的**非交互底图延伸层**产生 Airbnb 式上下连贯，但所有地图拖动/缩放手势只在中间内容视口命中，不能覆盖或穿透顶部控件。模糊能力或性能不足时降级为足够高遮罩的浅白背景；不能牺牲可读性。

### 8.3 地标是地点主体，底部是多类 Information Card 集合

- 使用真实 `place_id` 与核验坐标标记地点，四业务类别仍按蓝/黄/紫/绿区分；一个地点可关联**不同类别多张卡**，不能把地点当成单张商家介绍。
- 点击地点弹出**地图视口内部**的底部抽屉，支持 `peek`（建议占地图视口 26–32%）、`half`（50–60%）、`expanded`（78–86%）三档；抽屉永远不盖住顶部分类栏与底部全局 Tab。
- 抽屉显示地点名称、关联卡片数量、符合当前分类/搜索/筛选的卡片；**不再重复一排与顶部相同的「全部/就业/商家/社团/活动」Tab**。
- 同一点多类信息采用单个混合标记/数字聚合，卡片标签显示具体类别，避免四枚图钉重叠；无真实坐标的信息不在图上伪造点位。
- 点击集合卡主体 → Card-to-Mini-App；点击已启用 CTA → Button-to-Mini-Contract 或真实官方入口；点击卡中责任主体 → 人/组织/商家主页。

### 8.4 搜索、筛选、类别和返回（**共享单一状态**）

1. 从校园 `feed` 进入 `map`：保留 `selectedCategory + filters + query + feedDensity + feedScrollAnchor`；初始化至已核验的校区范围，非必需精确定位。
2. 地图态点击顶部分类或筛选：仅更新地图标记和地点集合；条件与信息流一致，不切回信息流。
3. 搜索输入在两视图均作用于**同一套已审核数据**；地图仅显示有有效地理关系的命中项，其他内容仍可在信息流中访问。
4. 从信息卡的地点字段进入地图：带入真实 `place_id` 自动选中；从 Mini-App 返回恢复其来源上下文。
5. 系统返回或再次点击「地点」：回之前的卡片密度/筛选/滚动位置，不额外增加一个全局 Tab。
6. 失效、无权限、无网络、无坐标：不展示假标记/距离，提供清晰空态与返回信息流入口。

### 8.5 V0 / V1 上线条件

地图 UI 壳与状态管理可先开发，仍属**第一阶段 P1 的数据就绪条件项**，不阻塞 P0 搜索浏览与胖达推荐。正式展示地点必须具备地图底图授权、`Place(place_id, campus_id, verified coordinates)`、`CardPlaceRelation`、校区边界、卡片可见性和有效期过滤。没有室内楼层数据不显示楼层菜单；没有精确定位授权也能手动选校区。

**详细界面层级、Token、抽屉三档、状态机、数据字典和 MAP-01–14 验收请以 `03_地点地图专题/地点地图_UI交互与状态规范_V1.2` 为准。**

## 09｜主体主页：自然落到人、组织和商家

### 9.1 统一容器

对于**长期存在的主体**（个人、社团/组织、商家），使用通用主体主页：**主页｜动态｜照片**。这三个 Tab 属于**主体二级页面的局部 Tab**，**不是**全局「校园｜胖达｜我」的替代品。

- 头部：圆形头像/Logo、主体名称、身份/资质标记（仅核验后）、个性签名/简介。
- 右侧：当前账户拥有管理权限时显示**编辑/设置**按钮；访问其他主体时不显示私有编辑入口。
- 操作区：公开访问者看到**关注｜连接**（连接进入消息），如存在真实能力可添加更明确的行动 CTA（加入/咨询）。
- **主页**：可编排介绍、服务、所属组织、关系图、重点卡片与地点组件；不是固定大表单。
- **动态**：公开的 Information Card 发布/更新记录；私人思考和未授权账本事件不自动公开。
- **照片**：此主体获授权公开的媒体资产视图；照片可关联具体 Information Card；不为凑内容自动生成假照片。

### 9.2 关联关系规范

- **个人 ↔ 商家**：例如「酸酸」个人主体与「酸酸美妆店」商家主体是两张独立档案，通过**经营者/创建者/负责人**等具体关系连接；两处可以互相跳转。
- **社团 ↔ 活动**：社团主体有独立主页；社团发布、主办或协办的活动是独立事件卡；活动页明确主办组织和实际负责人。
- **就业 ↔ 企业/发布者**：岗位页提供企业/组织卡与责任联系路径；没有真实个人负责人时不能编造。
- **地点 ↔ 主体**：一个地点可以聚合组织、商家、活动、岗位等多个关联卡；不能用地点替代组织或人。

**权限**：前台展示公开且经过授权的资料；学生隐私、联系方式、参与记录、服务/订单数据默认不因存在主体图谱就公开。

## 10｜Card-to-Mini-App：四类二级业务体验

> **阶段说明**：第一阶段二级 Mini-App 优先实现可信的**只读详情与真实联系方式/官方入口**。下述申请、预约、报名、加入等完整功能流程属第二阶段或需外部服务先完成接入，不能因模板上有 CTA 就被当作已实现。

### 10.1 统一容器，专属内容

二级 Mini-App 共享：顶部返回、主体/事项名称、发布与责任关联、权限状态、加载/异常反馈，以及与首页卡片的同一 ID。**内部功能区与页面模块依据类别和已声明能力变化**，不做统一八字段详情表单。

| 模板 | 二级内容结构 | 主要关系 | Card 点击 | CTA 点击 |
|---|---|---|---|---|
| **就业/创业机会** | 岗位概况 → 资格/要求 → 时间/地点/工作方式 → 企业信息 → 申请路径与状态 | 岗位 ↔ 企业/组织 ↔ 负责人 | 打开岗位 Mini-App | 「申请」进入已接入申请流程；未接入仅「查看申请方式/联系」 |
| **商家** | 店铺概况 → 服务/商品集合 → 经营者 → 地点/时间 → 公开评价与客服 | 商家 ↔ 经营者 ↔ 服务项目 | 打开商家主体主页 / Mini-App | 「咨询/查看服务/预约」按真实能力直达 |
| **社团/组织名片** | 主体简介 → 负责人/关系 → 近期活动卡 → 招新信息 → 联络方式 | 组织 ↔ 负责人 ↔ 活动 | 打开组织主体主页 | 「加入/连接」进入公开条件与处理流程 |
| **活动** | 活动介绍 → 主办组织/负责人 → 时间地点 → 参加条件 → 报名与参与记录 | 活动 ↔ 主办方 ↔ 参与主体 | 打开活动 Mini-App | 「报名/查看规则」按当前能力直达 |

### 10.2 具体跳转规则

- 信息卡**媒体**打开媒体预览；点击**标题/信息正文/非 CTA 的卡片区域**进入相应 Mini-App。
- 点击**大标签**只触发类别搜索/筛选，不打开经营服务；点击**地点**打开定位地图；点击**发布主体/负责人**进入其主体主页。
- 点击**关键 CTA** 进入对应 Mini-Contract；对于 V0 尚无能力的服务，**不得伪造「提交成功」**，要跳到真实联系、官方报名页或显示暂不可用说明。
- 页面内如可访问多个主体，显示明确的所属/经营/主办关系，而不是以“谁更高等级”为由隐藏主体链接。

## 11｜Button-to-Mini-Contract：行动入口的真实语义

**Mini-Contract 定义**：一项可执行行动的最小交互流程，可以是只读查询、提交咨询、报名意向或正式申请；**不等于必然成立法律合同**。它必须声明 `capability_id`、输入、前置条件、权限、执行方、真实状态、输出与责任归属。

- **就业申请**：资格/要求 → 材料与授权 → 实际提交或跳转 → 真实受理状态。
- **商家咨询/预约**：需求说明 → 联系/选择时间 → 商家确认 → 约定/履约记录；只有真实接入才显示「预约成功」。
- **社团加入**：招新条件 → 申请 → 组织审核 → 公开成员关系变更（经授权）。
- **活动报名**：参加条件 → 授权 → 提交 → 主办方受理/成功 → 可选签到与反馈。

**第一阶段最低实现**：必须能路由到有效的详情、官方链接或已接入的消息/联系渠道；未接入执行接口时退化为「联系/查看方式」，绝不制造付款、报名、申请或消息已发送的假结果。**主体直接建立合约、自动发起合作和完整履约状态写回属于第二阶段**。

## 12｜数据接入与主体模型（校园前端依赖）

### 12.1 稳定本体边界

所有内容归入 KUATO 模型：**主体账户（身份/属性/关系）＋ 活动账本（历史/版本/状态）＋ 活动合约（能力/条件/执行）**。界面只是这些数据在当前情境的投影。

V0 最小必备对象：`Entity`、`InformationCard`、`Place`、`EntityRelation`、`Capability`、`MediaAsset`、`ChangeLog`。复杂合同与自主发布机制可以暂时不执行，但**预留关联 ID 和状态字段**。

### 12.2 最小字段字典

| 字段 | 类型/含义 | 说明 |
|---|---|---|
| `entity_id` | string | 卡片承载的现实本体/事项 ID |
| `card_id` | string | 前台唯一卡片标识；三级缩放与地图一致 |
| `type` / `subtype` | enum | 四大类别与细分业务，不以 UI 文案充当数据库 ID |
| `title` / `summary` | string | 标题、摘要；前台长度需裁切 |
| `media_ids[]` | list | 媒体资源引用、显示权限和排序 |
| `time_info` | object | 时间值+含义（发生、截止、营业、有效）+时区 |
| `place_ids[]` | list | 可为空，关联地点主体、地理关系 |
| `key_facts[]` | list | 经过核对的关键条件/状态，小标签来源 |
| `metrics` | object | 真实浏览量、报名数、可用名额等；按展示阈值与权限处理 |
| `publisher_entity_id` | string | 实际发布主体 ID |
| `responsible_entity_ids[]` | list | 业务责任主体，可为组织/个人；关系类型需声明 |
| `created_by` / `on_behalf_of` | string | SFOS 代理录入者与被代理的真实主体分离 |
| `capabilities[]` | list | 能力 ID、可用状态、路由及执行方 |
| `publish_status` | enum | 草稿/待审核/已发布/已下架 |
| `valid_from` / `valid_until` | datetime? | 生效/失效，可选但优先采集 |
| `visibility` / `updated_at` | enum/datetime | 可见范围与最后核验/更新信息 |

### 12.3 前端接口依赖（建议）

- `listCards(query, filters, cursor, sort)` → 分页卡片列表、真实结果数与展示所需元数据。
- `getCard(card_id)` → 完整卡片、关系、CTA 路由和关联主体。
- `getEntity(entity_id)` → 公开主体主页、主页组件和动态/照片引用。
- `listPlaces({campusId,bounds,category,filters,query})` / `listCardsByPlace({placeId,filters,query})` → 地图点位与地点集合。
- `getCapability(capability_id)` → 条件、状态与可执行入口；前端不可硬编码所有类别都能「预约」。

**所有查询默认约束**：已审核 + 已生效 + 用户有权访问；历史内容进入档案并标记过期，不在默认有效机会信息流中误导展示。SFOS 代理上传不意味着信息真实责任统一归于 SFOS。

**第一阶段 Agent 只读工具建议**：`searchCampusCards(query, type?, time?, place?)` 返回卡片摘要与 `card_id`；`getCampusCard(card_id)` 获取明细及更新时间；`getPublicEntity(entity_id)` 获取公开责任主体；按角色控制可查询字段。所有工具应返回显式空结果与错误码，防止模型以自然语言猜测代替数据库事实。

## 14｜状态、权限与边界测试

- **无网络/失败**：保留已缓存的允许公开内容（若实现），明确陈旧状态；支持重试，不显示貌似实时的错误数据。
- **审核/失效**：被撤回或过期信息不得继续当作可用机会；分享旧链接展示「已结束/已下架」提示及主体联系路径（按权限）。
- **无定位**：允许访问地图并选择校区/地点；不强制获取精准位置；不能计算无依据的距离。
- **无权限主体**：联系人、成员、私有记录不公开；只有具有编辑授权的账户显示管理操作。
- **能力不可用**：按钮展示「暂不可用」或真实替代链接，不模拟申请已提交、付款已完成、预约已成功。
- **重复点击 CTA**：防重复提交；外链跳转与真实回执区分；状态以服务方确认的数据为准。
- **标签与色彩**：所有大标签至多两汉字且同标题同一行；默认浏览量=1000时隐藏，1001时可展示；列表不能把浏览量或不可用指标当作可信评价。

| A15 | 胖达请求「找适合设计专业的实习」 | 调用真实数据库只读工具，返回经过权限/有效性过滤的匹配卡、责任主体及推荐依据，点击能打开原卡 |
| A16 | 胖达被询问数据库不存在的服务 | 不编造商家/报名名额/价格，明确说明未找到或资料未核验，并建议更换关键词 |
| A17 | SFOS 更新、撤销或使卡片失效 | 校园搜索与胖达查询同步体现新版本/失效状态，不再推荐失效的机会 |
| A18 | 主体尝试在第一阶段自主发布或发起未接入的 Mini-Contract | 不提供无权限发布入口，不提示虚假成功；自主发布和合约创建明确标记为第二阶段 |
| A19 | 从卡片首页点击「地点」并返回 | **只有分类栏下方中间区域**在信息流与地图间切换；顶部四层和底部栏不移位；返回恢复原卡片密度与滚动 |
| A20 | 观察地图态背景 | 默认上栏目白底；地图态顶部四层渐变磨玻璃；底部白底不透明无 blur；分类行保留 |
| A21 | 地图态筛选、切换类别与搜索 | 沿用同一查询与分类状态；标记与地点集合结果一致；筛选后不强制回卡片视图 |
| A22 | 选中地点并上滑抽屉 | 同一个 `place_id` 能查看不同业务类别卡片；peek/half/expanded 抽屉不会遮挡顶部或底部固定栏 |
| A23 | 地图无坐标、无网络或无精确定位授权 | 不伪造位置、距离和实时状态；支持空态、重试、手选校区及返回信息流 |

**第一阶段交付判定（地图按 P1 数据就绪条件项验收）**：SFOS 代理上传经审核的四类试点信息 → 校园页可按分类搜索和三级语义缩放浏览 → 胖达能依据数据库对同一 `card_id` 进行准确问答与推荐 → 进入对应只读 Mini-App / 责任主体 / 真实有效的联系入口。地图在有真实校区坐标与地点数据时纳入验收，否则明确标记为后续联调，不得用虚构点位充数。

## 16｜开发阶段、协作交付与未决事项

### 16.1 第一阶段：搜索、浏览与 AI 百科式推荐（当前开发）

| 顺序 | 工作块 | 可验证交付 |
|---|---|---|
| S1-01 | 四类真实数据采集与运营录入 | SFOS 可创建/核验/上下架就业、商家、社团、活动资料；责任主体与代理录入者区分 |
| S1-02 | 数据库与信息卡接口 | 信息流读真实数据库；同一 `card_id` 支撑三档密度和二级详情 |
| S1-03 | 搜索、筛选与分类浏览 | 分类、关键词、基础维度组合、空结果和已失效信息处理正确 |
| S1-04 | 胖达数据库只读查询与推荐 | 学生提问后按已审核事实返回卡片、摘要、关联主体和可解释理由 |
| S1-05 | 联调、权限和首条完整闭环 | 代理录入 → 校园发现 → 胖达返回同卡 → 查看/联系，结果可复测 |

地点地图、基础主体主页按真实地点与核验资料的就绪情况作为条件项推进。**第一阶段不依赖自主发布或 Mini-Contract 的真实执行**。

### 16.2 第二阶段：Agent 辅助主体自主发布和合作（后续规划）

1. **核验并授权主体账户**：学生、商家、社团和学校组织能够管理各自有权发布的内容。
2. **Agent 协助创建信息卡**：主体以消息、图片或文件表达需求；胖达抽取结构化内容、标出缺失信息，生成草稿，人审核后发布，按需要经过校方/平台审查。
3. **主体持续维护**：自行更新服务、岗位、活动与社团信息；每次修改保留版本、操作人和生效状态。
4. **自主建立 Mini-Contract / 合作**：在实际接口、权限与处理方到位的前提下发起报名、申请、咨询、合作意向与履约，结果写入活动账本；不把意向误显示为成功履行。

第二阶段仍沿用第一阶段建立的 `entity_id`、`card_id`、发布主体与权限体系。阶段任务拆分、依赖、交付与人工勾选进度，详见单独文件 **《PANDA CAMPUS｜开发路线与进度 V1.2》**。

### 16.3 地点视图专项交付（V1.2）

- 交互产物：同框 `feed/map` 两态、顶部渐变磨玻璃、底部纯白栏、共享分类筛选、地图内容视口的抽屉三态。
- 数据产物：核验校区范围、地点实体与地理关系、`listPlaces`/`listCardsByPlace`、地图底图使用授权。
- 验收：采用《地点地图 UI 与交互规范 V1.2》MAP-01–14；地点数据未齐时将地图列为 **P1 待联调**，不得以虚构地图截图表示完成。

### 16.4 待业务确认（不可由开发者猜测）

- 首批四类业务的真实运营来源、合作方授权、核验负责人；各类可持续更新的数据量与有效期。
- 第一阶段胖达的问答范围、可用字段、推荐排序及日志授权规则；默认先用可解释的基础检索规则。
- 地图底图授权、真实坐标、试点校区范围、地点主体与卡片关联表；缺乏真实地点时只能交付不含假坐标的地图 UI 壳，不上线伪造地标。
- 商家/就业/社团/活动的真实联系或官方办理渠道，以及第二阶段能否接入可执行能力。
- 第二阶段主体认证、内容审批、发布权限与 Mini-Contract 执行方和证据规则。

**最终交付原则**：**第一阶段先让真实信息可持续进入数据库、可被检索和推荐；第二阶段再让真实主体在授权与审核下自己创建信息、建立合作并追踪合约结果。**
